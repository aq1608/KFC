# Conventions & Guardrails

## Security (non-negotiable)
- **Flags stay on the server.** Store them only in `challenges.seed.js` (and in
  the route/asset that legitimately reveals them as the puzzle). Never leak a
  flag in client-visible code that isn't itself the puzzle.
- **Locked content stays hidden server-side.** A locked challenge must not send
  its description/hints/writeup to the client; un-purchased hints and pre-solve
  writeups are withheld in the route, not just in the template.
- **Vulnerable challenges must be sandboxed.** Path-traversal, IDOR, and JWT
  challenges operate on in-memory data only — they must never touch the real
  filesystem or other users' data.
- Flags follow the `CHICKEN{...}` format.

## Data layer
- Route handlers are `async` and go through `store` (never a driver directly).
- Any new query is implemented in BOTH backends with identical behaviour.
- Prefer prepared statements (SQLite) / parameterised queries (Postgres).

## Testing
- Keep `npm test` green; the runner exits non-zero on failure and blocks CI.
- Every challenge gets a test proving its flag is reachable via the intended
  path (round-trip decode for crypto/rev, HTTP flow for interactive ones).
- Crypto/stego assets are generated by `tools/gen_challenges.js` and
  round-trip-verified — extend it rather than hand-crafting binaries.

## Git & CI workflow
- Feature work can be committed to `main`. **CI/workflow files under
  `.github/workflows/` must go via a pull request** (they run with secrets and
  need review) — the platform blocks pushing them straight to `main`.
- Deploys are gated on the test suite passing.

## Style
- CommonJS, 2-space indentation, semicolons — match surrounding code.
- No new runtime dependencies without good reason; the stack is deliberately small.
- Server-rendered EJS; any client-side JS should be small and dependency-free.
